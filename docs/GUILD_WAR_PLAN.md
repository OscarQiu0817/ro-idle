### 與原規劃的差異
原本第 2 步要把戰鬥函式全面改成「傳入行動者」並拔掉 `withAlly`。實作改用雙世界：
敵方隊伍在自己的 state 裡跑同一套引擎，不必重寫全部戰鬥函式，風險小很多。
`withAlly` 仍保留；之後若要做多隊同場（同一張圖三隊以上），再做全面的行動者改寫。

## 第 2 步的改法（逐步，不一次重寫）

1. 新增 `actorOf(x)`：玩家 state 與隊友物件都當成「行動者」，欄位統一
2. 先改傷害結算（普攻、技能傷害、受傷）吃行動者參數，`withAlly` 暫時保留當轉接層
3. 怪物清單改屬於地圖實例（`MapInstance.monsters`），玩家 state 只留引用
4. 敵對行動者放進地圖實例，與怪物並列為目標；AI 沿用隊友的自動施放
5. 全部改完再拔 `withAlly`

## 雲端提案（2026-11-13 使用者確認：要做、沒登入不能攻城、不做重播驗證、台灣時間；已實作）

後端是另一個專案 `world-chat`（Cloudflare Worker＋D1，已有帳號與雲端存檔 `src/cloud-save.ts`）。那邊的規則是一次一個階段、先問再做，所以這裡只列提案。

| 項目 | 提案 |
|---|---|
| 身分 | 沿用雲端存檔的帳號 token；沒登入不能攻城（本機版照舊可玩） |
| 資料表 | `castles`（castle_id、owner_account、owner_name、snapshot TEXT、since、version）＋ `castle_log`（castle_id、account、name、at、result），一個 D1 migration |
| 快照大小 | 一份約 9KB（三人）；上限 16KB，超過拒收 |
| `POST /castle/get` | 回傳城主名字、隊伍摘要、快照、version（挑戰前下載） |
| `POST /castle/capture` | 帶 token、castle_id、自己的快照、挑戰時的 version；version 不符＝別人先佔了，拒絕 |
| 時段 | 伺服器用台灣時間判斷 20:00～22:00，時段外拒收 |
| 快照驗證 | 人數 ≤3、等級 ≤ 上限、素質點數總和、精煉 ≤20、技能等級 ≤ 上限、大小；伺服器沒有道具資料庫，「道具存不存在」先不驗 |
| 勝負驗證 | 伺服器跑不動整套遊戲引擎（Worker 免費方案 CPU 10ms），**不做重播驗證**；只靠時段＋version＋限流 |
| 限流 | 沿用 ratelimits：每帳號每分鐘 3 次 capture |
| 每日 10 點 | 點數存在玩家自己的存檔裡；遊戲端讀 `/castle/get` 確認自己是城主才發（伺服器不經手點數） |
| 成本 | 每次挑戰 1 讀、佔領 1 寫；都在免費額度內 |

需要確認：①要不要做 ②沒登入能不能攻城 ③不做重播驗證可以接受嗎 ④時區用台灣時間。
